## 1. 产品定位与目标

面向正在准备 Java 后端面试的学生和初级开发者，帮助使用者把“知道知识点”练成“能独立讲清楚、能回答追问”。

核心目标：内容正确、表达清楚、经得起追问。完整模拟面试作为阶段验收入口，日常使用围绕单题练习、项目表达和针对性复练。

产品主张：**每次练习都让用户知道自己哪里没讲清楚，并有机会再次回答、验证改进。**

### 1.1 首版范围

| 项目 | 首版决定 |
| --- | --- |
| 岗位范围 | Java 后端，先覆盖 Redis、MySQL、Spring、Kafka、线程池和 JVM |
| 使用方式 | 个人自部署、单人练习；公开多用户服务另列扩展任务 |
| 首批题量 | 24 道精选题，每个主题 4 道，逐题维护评分依据 |
| 练习形态 | 先完成文字训练，再增加录音回答、转写和回放 |
| 每日练习 | 默认推荐 3 道题，允许自主选题和结束练习 |
| AI 职责 | 依据题目要点和参考资料识别问题，帮助组织回答，生成针对性追问 |
| 内容原则 | 接受不同的正确表达；项目事实由用户提供，缺失信息明确标注 |
| 进度依据 | 有效的独立回答和延迟复测；阅读解析、点击“掌握”不算掌握证据 |

首版不扩展到全行业题库，不增加社交、招聘、收费会员或企业后台。继续使用现有技术栈；暂不拆微服务或引入新的消息中间件。

### 1.2 典型使用场景

1. 用户背过缓存与事务知识，但讲出来只有一句术语。系统指出遗漏，并让用户重新解释。
2. 用户项目介绍像技术清单。系统帮助他补齐业务背景、个人职责、选择原因和结果证据。
3. 用户看完解析觉得懂了，过几天仍答不出。系统安排换一种问法的复测。
4. 用户想练口头回答。录音后先核对转写，再看结构反馈和回放自己的表达。

## 3. 用户训练闭环

```text
选择题目
  ↓
不看答案，独立回答（文字 / 录音）
  ↓
逐项反馈：答对什么、漏了什么、哪里错误、哪里讲不清楚
  ↓
查看相关知识和回答组织建议
  ↓
重新回答 → 对比两次回答的具体变化
  ↓
针对薄弱点回答一个追问
  ↓
加入复习计划 → 延迟复测 → 更新掌握状态
```

同题练习保留每次回答，不覆盖第一次回答。练习会记录是否看过解析、是否使用提示，区分“刚看完后会答”和“隔几天独立答出”。

### 3.1 完整示例

题目：“秒杀活动如何避免库存超卖？”

用户首次回答：“用 Redis Lua，因为 Lua 是原子的。”

系统反馈：

| 要点 | 判定 | 给用户的解释 |
| --- | --- | --- |
| 说明并发读改写的风险 | 缺失 | 没有解释普通读库存、判断、扣减为什么会出现竞态 |
| 判断和扣减在同一短脚本中执行 | 部分覆盖 | 提到了原子性，但没有说明脚本覆盖哪些操作 |
| 明确原子性的作用范围 | 缺失 | Redis 操作的原子性不代表订单数据库事务也被覆盖 |
| 说明失败补偿与请求幂等 | 缺失 | 还需解释订单创建失败和重复请求如何处理 |

练习建议：“先讲竞态窗口，再讲脚本如何覆盖判断与扣减，最后说明跨系统失败和重复请求的处理边界。”

用户重新回答后，系统逐项比较：补上了哪些遗漏、哪些错误已修正、哪些问题仍然存在。接着追问：“库存扣减成功，但订单数据库写入失败，你会怎么处理？”

若用户在介绍自己的项目，系统必须区分“项目已实现的处理”和“建议补充的方案”；不能把补偿机制自动写成用户已完成的工作。

## 5. 评估与内容规则

### 5.1 每道题的内容结构

每题必须具备稳定 ID、版本、主题、知识点 ID、难度、题干、建议回答时长、必答点、易错点、接受的替代表述、解释资料、来源和追问模板。

知识点 ID 用于跨题复习，例如 `redis.lua.atomic-scope`。多个题目可以测同一知识点；换题不意味着该知识点重新从零累计。

首批 24 题建议：

| 主题 | 四个方向 |
| --- | --- |
| Redis | Lua 库存扣减、锁所有权与过期、淘汰策略、持久化丢失窗口 |
| MySQL | 慢查询与执行计划、联合索引、隔离级别、MVCC 与锁定读取 |
| Spring | 代理与自调用、异常回滚、事务传播、异步与事务边界 |
| Kafka | 生产可靠性、重复消费、offset 提交时机、分区顺序边界 |
| Java 线程池 | 线程数与队列、无界队列、拒绝策略、关闭与任务超时 |
| JVM | GC 排查、堆与堆外内存、泄漏引用链、堆转储采集边界 |

P1 已按这些方向完成 24 道题及官方资料核对。题目绑定独立的版本化评分依据，已有知识卡继续用于原模拟面试；P2 已接入实际模型逐项判定和单题训练闭环。

### 5.2 结构化评估

知识判定采用五种状态：`COVERED`、`PARTIAL`、`MISSING`、`INCORRECT`、`UNCERTAIN`。每个要点分别存储判定、候选人原话、判断理由、参考依据。

- 不能用是否出现术语替代语义判断；正确的口语解释也应被认可。
- 引用原话必须能在提交的原始回答中定位；“缺失”可以没有原话，不能捏造引用。
- 知识覆盖与知识正确性分别呈现；“都提到了但理解错误”不能被算成掌握。
- 知识不足、参考不足、回答歧义时允许 `UNCERTAIN`，不能硬判为错误或通过。
- 相似度是检索指标，不是答案正确率；不把 Chroma 分数直接转成面试分数。
- 主界面展示要点判定与建议；整体数字只做辅助，不能声称预测面试通过率。
- 表达建议至少说明具体问题和下一次如何改，避免只有“表达更清晰”等泛泛评价。
- 不强迫用户背统一措辞，不因口音、说话速度或声音特点直接判断知识掌握。

评估结果保留问题版本、评分标准版本、回答快照、参考片段快照、模型标识、提示词版本和时间。历史结果按当时版本展示；需要重新评估时增加新记录，不能静默覆盖。

### 5.3 辅助与独立表现

练习记录中保存 `hintsUsed`、`referenceViewed`、`inputMode`、`parentAttemptId`。重答对比优先比较同题、同评分版本的有效结果；版本或题型改变时明确说明不可直接比较。

阅读解析后的重答用于反馈改进，不能单凭这一结果判为长期掌握。延迟复测时隐藏原解析与前次答案；完成后再允许对照。

## 6. 六阶段实施路线

当前 P1、P2、P4 已完成验收，P3 代码与本地检查完成，真实语音与设备验收待补；P5、P6 未开始。每阶段完成后更新第 11 节的记录；达到验收标准后再进入依赖它的阶段。

| 阶段 | 目标 | 前置依赖 | 可交付的价值 |
| --- | --- | --- | --- |
| P1 | 精选题库与可核验评分依据 | 现有 RAG | 有可靠的练习题和要点评判基础 |
| P2 | 单题训练、重答与逐项反馈 | P1 | 用户可以完整练一道题并看到改进 |
| P3 | 录音、转写、回放与口头表达反馈 | P2 | 用户能练实际口头回答 |
| P4 | 真实项目材料与项目话术训练 | P2 | 用户能把自己的经历讲清楚 |
| P5 | 薄弱点、延迟复测与每日计划 | P2；兼容 P3/P4 | 用户知道接下来该练什么 |
| P6 | 效果评测、演示和交付完善 | P1–P5 | 有可复现的工程和使用效果证据 |

推荐按 P1 → P2 → P3 → P4 → P5 → P6 实施。P3、P4 都依赖 P2，可以根据实际使用需要调整先后；文档不预设并行开发。

### P1：精选题库与评分依据

**用户目标：** 能选到有明确训练价值的题目，每道题的知识判断都有依据。

实施任务：

1. 新增题目、知识点、评分要点的数据结构和版本规则。
2. 整理 24 道题，逐项核对官方资料；题库从仓库内版本化资源导入 MySQL，重复导入不产生重复题目。
3. 实现按主题、难度筛选的分页查询与题目详情。首答前的题目响应不包含参考答案或完整评分标准。
4. 在评分资料与 Chroma 知识文档之间建立稳定映射，保留来源和引用版本。
5. 新增评估输出 DTO、严格解析与字段校验；训练评分独立于现有 `AnswerAssessment`。
6. 建立不少于 24 条固定回答样例，至少覆盖正确口语表达、缺失、事实错误、无关回答、含错误术语及证据不足六类情况。

验收标准：

- [x] 24 道题均有题目版本、稳定知识点 ID、必答点、易错点和可核验来源。
- [x] 重复导入后题目数量不增加，修订题目不会破坏历史引用。
- [x] 筛选、分页、无结果和非法参数处理正确。
- [x] 未提交首答前的正常题目接口不直接返回解析。
- [x] 非法评估输出、不存在的原话引用、虚构来源被识别，不能作为正常成绩保存。
- [x] 来源核对和固定样例检查结果写入阶段验收记录。

本阶段不改整场面试状态机，不开发语音或每日计划。P1 为基础交付，完整用户闭环在 P2 实现。

### P2：单题训练与重答闭环

**用户目标：** 选一题，独立回答，看具体反馈，再答一次并看到变化。

实施任务：

1. 新增题库、单题训练和练习历史页面，复用现有布局与基础组件。
2. 每次提交创建不可变的回答记录，保存题目版本、辅助使用情况与父回答 ID。
3. 通过题目评分标准、相关 RAG 片段与回答进行逐项评估；展示知识反馈、表达建议和依据。
4. 提供“查看解析”“再答一次”“练一个追问”三个清晰操作。
5. 重答后以要点 ID 对比前后回答，显示新覆盖项、纠正项、仍有的问题和不可判断项。
6. 新增训练流程及合法状态转换；处理重复点击、刷新、评估失败、重试与中途离开。

验收标准：

- [x] 桌面与手机均能完整完成“选题—首答—反馈—重答—对比—追问”。
- [x] 不覆盖首答；刷新页面后能恢复回答和评估进度。
- [x] 同一次提交重复发送只产生一条回答和一个有效评估任务。
- [x] 模型失败时保留回答，显示可重试状态；不会出现伪造分数或空白成功页面。
- [x] 正确的不同措辞能通过评判；无关回答不能因命中几个关键词就被认定掌握。
- [x] RAG 不可用时明确说明参考不足；有足够的已核验题目资料时允许有限评估，否则相关要点标为无法判断。
- [x] 在固定样例上记录模型判定与预期判定的差异，逐项修正明显错误。
- [x] 原模拟面试、历史记录和报告入口仍可使用。

验收环境为内置 Chromium 桌面及 390×844 手机视口；真实模型固定集为 20 次调用及 4 条无来源程序判定，72 个要点与人工预期相同。样例同时用于校准，不代表未见答案的准确率。流程、故障恢复、测试与截图见 [P2 验收记录](p2-acceptance.md)。

完成 P2 后即可开始个人实际练习；不要等到所有阶段完成才试用。

### P3：录音与口头表达练习

**用户目标：** 对着题目真正说一遍，听回自己的回答，再练一次。

实施任务：

1. 支持开始录音、计时、停止、回放、重新录制；默认单段最长 180 秒。
2. 新增音频存储与转写任务，通过供应商适配接口接入实际语音识别服务；语音配置独立于 DeepSeek 文本配置。
3. 实施前按当前官方文档核对服务支持的格式、大小、认证与费用，选择一个实际可用实现并写入配置说明。
4. 展示转写草稿，允许用户修订；评估以用户确认提交的文本为准，音频与原始转写另行保存。
5. 把口头回答接入 P2 的逐项评估和重答对比，支持原音频回放。

### P4：真实项目话术训练

**用户目标：** 把自己的项目经历讲得可信、具体、条理清楚。

### P5：薄弱点、每日计划与延迟复测

**用户目标：** 清楚今天应该练什么，并检验是否真的记住、讲清楚了。

实施任务：

1. 基于知识点 ID 持久化薄弱点，关联造成该判定的练习与证据。
2. 掌握状态采用“未练习—练习中—待巩固—已巩固”；状态与到期复习分别记录。
3. 创建可配置的简单复习规则：首次有效练习后 1 天、3 天、7 天安排复测；这是初始产品规则，可由使用者自行调整。
4. 复测错误时回到较短间隔；是否使用提示与解析影响掌握判定。默认至少两次分开的独立有效复测通过，才标为已巩固。
5. 推荐优先级：到期复习 → 最近未解决错误 → 未练新题。用户可修改当天题量。
6. 构建今日练习、薄弱点和进步记录页面，显示每道推荐题的原因。

验收标准：

- [x] 同一知识点跨不同题目累计练习，不依赖自由文本描述去猜测是否相同。
- [x] 使用提示后的一次高分不直接把知识点标为已巩固。
- [x] 未完成或失败的评估不会更新掌握状态。
- [x] 重复处理同一评估不会重复安排复习或累加进度。
- [x] 时区、当天边界、逾期、暂停和恢复规则明确；逾期任务不成倍堆积。
- [x] MySQL 保存长期进度；清空 Redis 或重启后不会丢失复习计划。
- [x] 进步图展示有效回答与独立复测，明确区分未评估、不确定和掌握。
- [x] 用户能够跳过推荐、自主选题和删除训练记录；删除后相关汇总重算或明确标为无证据。

说明：复测安排借鉴主动回忆与间隔练习思路。研究支持主动回忆有助于长期记忆，但这里的 1/3/7 天规则和面试效果需要自行验证，不作为科学最优间隔或通过率承诺。[研究依据](https://pubmed.ncbi.nlm.nih.gov/16507066/)

### 7.4 状态和失败处理

评估任务状态：`PENDING → RUNNING → SUCCEEDED / FAILED`。失败任务可以显式重试；只有合法、已校验证据的成功评估参与对比和复习计算。

- 模型调用不占用长时间数据库事务；先保存回答与任务，再执行评估。
- 使用受限线程池执行任务，保存任务状态；重启后识别中断任务并恢复或标为可重试。
- 设置超时、输入长度与输出校验；自动重试有明确上限，不能无限消耗模型调用。
- 重试不重复插入回答、重复扣除进度或重复安排复习。
- 记录错误类别、耗时和版本；默认日志不输出完整简历、录音或密钥。
- 参考资料作为数据处理，不能执行其中的指令；对判定依据和原话做程序校验。
- 失败和不确定状态在界面可见；不要用通用“成功评分”掩盖模型或检索故障。
